**CRITICAL PATTERNS:**
- `params` is a Promise in Next.js 15/16 — ALWAYS `await params` in async server components
- Use `createServerSupabaseClient()` for ALL data fetching — never use admin client for page queries
- Query `active_*` views (not raw tables) — these filter soft-deleted rows
- If Supabase query returns empty, call `notFound()` from `next/navigation` — this triggers not-found.tsx
- Pillar color comes from DB as hex string — use inline `style` for dynamic color, NOT Tailwind arbitrary values

**BREADCRUMB WIRING PATTERN:**
Each page is a server component that fetches its own data. The breadcrumb pattern is:
1. Page fetches entity data from Supabase (e.g., pillar name from slug)
2. Page calls `buildBreadcrumbs()` with resolved names
3. Page renders a wrapper that includes `<Header breadcrumbItems={crumbs} accentColor={pillar.color} />`

However, since Header is already rendered in the root layout, we need a different approach. The recommended pattern:

**Option A (Recommended): Page-level layout wrapper pattern.**
Each page renders its own content. The root layout renders a basic Header with just "Dashboard" breadcrumb. Each hierarchy page overrides the breadcrumb data by using a **React context** or **per-page layout**.

**Implementation: Use a BreadcrumbContext.** Create a minimal client context that pages can populate:
- Root layout renders Header which reads breadcrumb items from context (defaults to Dashboard only)
- Each page wraps its content in a `<BreadcrumbSetter items={crumbs} />` client component that updates the context
- This avoids prop-drilling through layouts and works with the single Header in root layout

**ALTERNATIVE if context feels heavy:** Remove Header from root layout. Instead, each page imports and renders Header with its own breadcrumb props. This is more explicit but duplicates the Header import. Given only 5 pages, this is acceptable. Choose whichever approach is cleaner — the key requirement is that breadcrumbs update correctly at every hierarchy level.
